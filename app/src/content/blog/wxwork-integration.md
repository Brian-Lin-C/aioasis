> 真实项目复盘第二篇。公司、客户、服务器信息均已脱敏；企微的 corpid、secret 等凭据用化名指代，技术细节全部保留。专有名词首次出现都会解释。

## 这篇为什么值得写细一点

企业微信集成是整个系统**外部依赖最重**的部分：登录靠它、通知靠它、连"能不能发消息"都要看它的规则脸色。复盘时我数了一下，相关代码五个模块、一千两百多行——大部分是 AI 写的，我复盘前只能说出"能登录、能发卡片"这八个字。

这篇文章就是我逐层审问的记录。企微集成拆开是**三条链路**：

1. **登录链**：员工怎么进来（手机 H5 无感登录 + 桌面扫码）
2. **推送链**：系统怎么找到人（提交记录后管理员收卡片通知）
3. **回调链**：企微怎么找到系统（用户给应用发消息，推给我们的服务器）

三条链共用一套凭据：**corpid**（企业 ID，相当于公司在企微的户口号）+ **corpsecret**（自建应用的密码）+ **agentid**（应用编号）。回调链额外多一对：Token 和 EncodingAESKey（消息加解密用的密钥，后面细说）。

## 链路一：登录——员工是怎么进来的

### 先把 OAuth2 流程画出来

**OAuth2** 是"第三方授权登录"的标准流程，微信扫码登录、Google 登录都是它。企微版本长这样：

```
员工手机                 我的服务器                企微服务器
   |                        |                         |
   |--1.打开 H5 页面-------->|                         |
   |                        |--2.跳转到企微授权页----->|
   |--3.员工确认身份(无感)-->|                         |
   |                        |<-4.带回一个 code--------|
   |--5.把 code 发给后端---->|                         |
   |                        |--6.code+secret 换身份--->|
   |                        |<-7.返回 UserId----------|
   |<-8.签发 JWT 登录成功----|                         |
```

第 4 步的 **code** 是一次性的临时凭证（几分钟内有效、用一次就废），它不证明"你是谁"，只证明"企微刚认证过你"。真正的身份交换发生在第 6 步——**服务器对服务器**：后端拿着 code + corpid + corpsecret 去调企微的 `getuserinfo` 接口，换回这个员工的 **UserId**（企微内部工号）。

最后第 8 步，后端签发自己的 **JWT**（一种自包含的登录令牌：把用户 ID、角色、版本号签进去，之后每次请求带着它，服务器验签名就知道是谁，不用查库）。

### 我的疑惑①：拿到 UserId 之后，用户在系统里怎么建档？

AI 的做法是"**查找或创建**"（find or create）：UserId 直接当用户名（企微工号天然实名、不会重复），第一次登录自动建账号，角色默认一线员工。

但有个细节我追问了：**姓名和手机号以谁为准？** 答案是企微通讯录——每次登录都同步一次，员工在企微改了名字，系统里跟着变。

然后我发现一个红队审出来的兜底：同步通讯录这步如果失败（企微接口挂了、网络超时、DNS 抖动），**登录不阻塞**，名字下次登录再同步。原来的代码只 catch 了一种异常，其他网络异常会直接穿透成 500 把员工拒之门外。

> **教训：凡是"锦上添花"的外部调用，兜底要宽到"挂了也无所谓"。** 登录是命脉，同步资料是附属——附属的失败不能砸命脉的锅。

### 我的疑惑②：一个人能在几台设备上同时登录？

AI 给了一个分情况答案：移动端（师傅们的手机）多端共存，互不踢；但超级管理员在桌面扫码登录时，**单点登录**——新登录会把旧会话踢掉。

实现方式很巧：JWT 里塞了一个 `token_version` 字段，管理员桌面登录时这个版本号 +1，旧令牌因为版本对不上自动失效。不用维护会话表，改一个数字就踢人。

### 我的疑惑③：本地开发没有企微环境怎么办？

代码里有个 `WXWORK_DEV_MODE` 开关：开发模式下 code 直接当 UserId 用，可以模拟任意身份。但注释里写着一句硬话：**生产环境必须设为 false**。

这就是第一篇说的"关键配置硬校验"思路——开发后门本身不可怕，可怕的是后门静默留在生产环境。这类开关的标准做法：启动时检查，生产环境检测到它开着就拒绝启动。

## 链路二：推送——通知是怎么 reliably 送到管理员手机上的

这是五条链路里最有料的一条，也是"AI 背着我都建了什么"最集中的地方。它是**演进出来的**，值得从演化史讲。

### 第一版的问题：进程一崩，通知就丢

最初的方案很直觉：员工提交记录 → 用 FastAPI 的 BackgroundTasks（请求返回后在后台执行的任务）直接调企微发卡片。

看起来没问题，直到有人追问一句：**后台任务还没跑完，进程重启了怎么办？** 答案是会丢——OOM、发版重启、服务器抖动，任何一个都能让通知无声无息消失。而且员工已经看到"提交成功"了，没人知道通知没发出去。

### 第二版：outbox 模式

AI 把它重构成了 **outbox 模式**（发件箱模式：先把"要发的消息"存进数据库的一张表里，再由发送器去投递）。这是企业系统里保证消息不丢的经典模式，拆开是四个设计：

**设计一：和业务记录同一个事务写入。**

员工提交维保记录时，`notification_outbox` 表在同一笔数据库事务里插一行"待发送"。**同事务**意味着：记录提交成功，通知一定在表里；记录回滚，通知也不会残留。从根上消灭"记录有了通知丢了"的缝隙。

**设计二：两条投递路径，即时 + 兜底。**

- **即时路径**：提交后 BackgroundTasks 立刻发送这行——正常情况用户无感，和以前一样快
- **兜底路径**：一个定时任务每 5 分钟扫一遍表，把还停留在"待发送"的行捞出来补发——进程崩了的残留全归它管

两条路径抢同一行怎么办？数据库**行锁**：即时路径用 `FOR UPDATE`（锁住这行，别人等），兜底路径用 `FOR UPDATE SKIP LOCKED`（锁住的就跳过——多实例同时扫表也不会重复发）。

**设计三：失败退避 + 封顶升告警。**

发送失败不是立刻重试，而是按**退避**节奏来：1 分钟、5 分钟、30 分钟、2 小时、8 小时——连续失败说明企微通道大概率出问题了，越试越没意义，不如拉开间隔。**连续 5 次失败后标记 failed，升级成运维告警叫人介入**，不再自动重试。

这里还有个细到可怕的考虑：发送时点如果管理员把通知开关关了，这条通知按"丢弃"处理而不是滞留——否则重开开关时，关闭期积压的通知会一股脑涌出来轰炸所有人。**防骚扰优先于补发。**

**设计四：at-least-once 语义。**

**at-least-once**（至少送达一次）和 **at-most-once**（最多一次）是消息投递的两种保证：前者可能重复但不丢，后者不重复但可能丢。这个系统选前者——发送成功但状态提交前崩溃，会被重投一次。通知场景多收一张卡片总比漏收强。

### 我的疑惑④：access_token 管理有什么讲究？

第一篇提过 access_token 会缓存。推送链路把缓存的几个坑全趟了：

- **提前 5 分钟过期**：官方说 7200 秒有效，本地按 6900 秒算——否则边界时刻拿着将死未死的 token 去调用，必然翻车
- **防惊群**：token 过期瞬间，几十个并发请求会同时发现"过期了"然后齐刷刷去重新获取。解法是**双重判定加锁**：抢锁前查一次，抢到锁再查一次——第二个判定保证实际只发一次请求
- **token 失效自愈**：企微返回 40014/42001 这类"token 无效"错误码时（比如 secret 被重置），自动清缓存、重取 token、重试一次——否则死 token 会在缓存里躺两个小时，期间全量调用失败
- **网络抖动自愈**：超时/连接重置自动重试一次——原来抖一下就丢一条通知

### 我的疑惑⑤：errcode 60020 是怎么回事？

这是企微文档写了但很容易被忽略的一堵墙：**自建应用发消息，服务器公网 IP 必须加入应用的「企业可信 IP」名单**，否则所有发送静默失败，错误码 60020。刚部署时通知发不出去，查日志就是这个。

注意它和备案、域名完全无关——只认服务器 IP。迁移服务器后第一件事就是更新这个名单。

## 链路三：回调——企微找上门时的安全手续

第三条链是反方向的：员工在企微里给应用发消息，企微推送我们的服务器。这条链处理两件事。

### URL 验证（一次性握手）

在企微后台配置回调地址时，企微会先发一个 GET 请求"验明正身"：带着签名和一个加密的 `echostr`。服务器要**校验签名 → 解密 echostr → 把明文原样返回**，企微看到正确明文才认这个地址。

### 验签与解密（每次推送都要做）

企微的加密方案在代码里体现为一个 `WXBizMsgCrypt` 类，我请 AI 把它逐行讲了一遍：

- **算法**：AES-256-CBC（一种对称加密：同一把钥匙加密解密；CBC 是它的工作模式）。密钥由回调配置里的 EncodingAESKey 派生
- **签名**：把 token、时间戳、随机数、密文排序拼接后算 SHA1——防篡改
- **明文结构**：16 字节随机头 + 4 字节消息长度 + 消息本体 + corpid——末尾的 corpid 用来校验"这条消息确实是发给我们企业的"

真正让我意识到"安全细节不在教程里"的，是红队在这个类里审出的三个问题：

1. **签名比较用了恒时间比较**。普通的 `!=` 比较是逐字符短路——第几位不匹配就第几位停，攻击者理论上能根据响应时间的细微差别逐位探测出正确签名（这叫**时序侧信道**）。`hmac.compare_digest` 不管第几位不匹配都花同样时间，堵上这个洞。
2. **PKCS7 垫片先验后取**。CBC 解密出来的内容末尾有填充字节，原实现直接按末字节数值切掉填充——攻击者篡改密文后末字节是随机数，切错了会静默吞数据或抛诡异的越界错误。先严格校验填充格式，被篡改立刻明确报错。
3. **验证失败对外只说"验证失败"**。原代码把"签名不匹配/corpid 不符"这种细节直接回显给请求方——等于免费教攻击者怎么调整。细节只进服务端日志。

> **教训：手写加密相关代码，一定要让红队过一遍。** 教科书只教算法怎么实现，不教这些"实现对了算法、做错了安全"的坑。

### 一个附带发现

回调配置成功，是开通「企业可信 IP」的**前置条件**——企微的规则。所以即使你的系统不需要收消息，回调 URL 也得配置并通过验证。文档不会把这个因果关系写在显眼处。

## 附：企微集成的注意事项清单

在第一篇七条铁律之外，这一篇补上企微专属的：

1. **凭据分级保管**：corpid/corpsecret/agentid 放 `.env`，不进代码库；secret 泄露等于别人能以你企业名义发消息
2. **IP 变更是运维事件**：服务器迁移、弹性 IP 更换后，第一时间更新「企业可信 IP」，否则通知静默全挂
3. **外部调用都设超时**：企微接口全部 10 秒超时——不设置超时的 HTTP 调用，就是把系统的稳定性抵押给对方
4. **开发模式开关要有生产防线**：`WXWORK_DEV_MODE` 这类后门，生产启动时必须自检
5. **通知快照要在入队时定型**：卡片内容在写入 outbox 那一刻冻结——记录事后被编辑，不影响已经发出的通知说的是当时的事实
6. **回调验签失败别回显细节**：对内详细日志，对外统一模糊

## 写在最后

审完这三条链路，我对"AI 帮我建了什么"终于有了实感：它不只是一个"能用的登录"和一个"能发的通知"，而是一套有崩溃兜底、有退避策略、有防骚扰、有安全加固的完整链路。很多设计（outbox、行锁防并发、恒时间比较）已经超出"教程代码"的范畴，是正经的工程做法。

但同时也看清了自己的位置：**这些东西 AI 能建，但只有人能审。** 审不出来的前提是你得知道该问什么——这就是这个系列存在的意义。
