> 本文是真实项目复盘的第一篇。公司、客户、服务器等信息均已脱敏，技术细节全部保留。文里的专有名词都会在首次出现时顺手解释。

## 先坦白：这个系统 mostly 是 AI 写的

去年我开发了一套设备运维管理系统：一线师傅手机拍照登记维保和报修，管理员桌面端汇总台账、统计材料、追踪工单，对接企业微信，照片进私有对象存储，数据库 PostgreSQL（目前最主流的开源关系型数据库之一）。

开发方式是我和 AI 结对——也就是现在大家说的 **vibe coding**（人只出意图和判断，代码主要由 AI 生成）。我出需求、做取舍、跑验收，AI 出方案、写代码、补文档。

项目上线后我复盘，发现一件有点心虚的事：**AI 从头到尾没提过 Redis 和 MQ，而我当时居然也没追问。** 技术栈就是 FastAPI（一个高性能的 Python 异步 Web 框架）+ PostgreSQL 15 + Vue3，没了。

几乎每个听说的人第一反应都是：这是玩具吧？企业系统没有缓存没有队列？

这个问题我答不上来，就是隐患。于是我把 AI 拉回来"答辩"了一次。这篇就是答辩记录。

## 第一轮审问：为什么不要 Redis？

先解释下 **Redis**：一个把数据放在内存里的缓存数据库，读写极快，企业系统常拿它给数据库"挡子弹"——热点数据先查它，查不到再查数据库。

AI 给的答案展开后是一本账，我把它核对了一遍，确实成立：

**先算量级。** 用户是维保项目的几十号人，高峰写入是拍照登记、一天几百条，最重的读操作是管理端汇总统计、扫几万行。这个量级 PostgreSQL 自己就是缓存——它有个叫 **shared_buffers** 的内存区域，热数据会自动留在里面，查询毫秒级。

**再算成本。** 引入 Redis 带来的不是性能提升，而是：多一个要监控的进程、多一份要备份的数据、多一类"缓存和库不一致"的 bug、半夜多一个可能挂掉的东西。

**小团队的架构第一原则不是性能最优，是能睡整觉。** 每少一个组件，半夜就少接一个告警电话。

我的第一个教训就在这：**AI 的默认方案往往是"教科书正确"的——它会基于常见最佳实践给答案，但最佳实践是有量级前提的。** 你得主动把真实业务量报给它，让它重新算账。如果我当时是日活十万的场景，它的方案会完全不同。

## 第二轮审问：那缓存需求真没有吗？

有，四处：企业微信 **access_token**（调用企微接口的临时钥匙，官方每 7200 秒强制过期一次）、通讯录、通知接收人列表、通知开关。

AI 的处理是进程内 dict（字典，一种键值对数据结构）加 **TTL**（Time To Live，存活时间——过了这个时间就当作过期，重新去拉）。

我追问"两个 worker（工作进程，服务器一般会开多个进程分担请求）各存各的，不一致怎么办"，它反问了一句把我说服了：

> 这些数据本来就不保证强一致。access_token 官方就是 7200 秒过期，通讯录能容忍秒级延迟，缓存 miss（没命中）就去官方接口再拉一次，重建成本几乎为零。

**缓存方案要配得上数据的语义，而不是反过来。** 有 TTL 语义、能容忍不一致、重建便宜的数据，进程内缓存就是最优解；Redis 是给"多实例共享、需要持久、结构复杂"的数据准备的，这个系统里没有这种数据。

## 第三轮审问：没有 MQ，异步和失败重试怎么保证？

**MQ**（Message Queue，消息队列）是另一种常见中间件：把"现在来不及做/怕做失败"的任务先扔进队列排队，由后台慢慢消费，作用是**削峰**（流量突然暴涨时排队缓冲）和**解耦**（两个系统不直接互相调用，靠队列传话）。

这是我最担心的一轮。系统里确实有异步需求：企微通知发送会失败要重发、照片处理慢、导出任务重。

AI 的解法是：**这些需求的关键词是可靠，不是快。**

- 通知发送落一张任务表，失败留痕，有专门的重发服务扫描重试
- 慢 SQL 开 `log_min_duration_statement=1000`（数据库自带的慢查询日志：执行超过 1000 毫秒的 SQL 自动记下来）落日志，每周翻一次
- 导出后台跑，跑完发通知

MQ 解决的是削峰和解耦。我既没有峰要削，也只有单体一个服务。而且落了任务表之后，"队列"其实已经在 PostgreSQL 里了，真要升级，换个消费者就是。**没有它解决不了的问题，就不要请它进来。**

## 最重要的一课：让每个决策交代"保质期"

三轮答辩下来，AI 的方案都成立。但我学到的最有价值的东西不是这些答案，而是一种审问方式——**让它说清楚每个决策什么时候失效：**

- 业务量涨十倍、汇总统计开始卡 → 该上缓存层了
- 拆出第二个服务需要共享状态 → 进程内缓存立刻失效
- 出现真正的流量尖峰 → 还是得排队削峰

到那天，PostgreSQL 里的任务表就是现成的迁移基础。架构决策不是结婚，是租房：按当下的负担能力住，留好搬家的路。

vibe coding 最容易出的问题，就是把 AI 的方案当成"完成态"照单全收。**方案没有保质期标签的，一律打回去重问。**

## 附：我总结的 vibe coding 注意事项

这是第一篇，先把贯穿全项目的几条铁律放在这，后面每篇再展开具体的坑：

1. **报真实量级，再谈方案。** 不说用户量和数据量，AI 只能给教科书默认值。
2. **看不懂的代码不让过。** 连接池、事务边界、并发控制这些，让 AI 讲到你能复述为止——上线后出问题时，debug 的是你不是它。
3. **安全不能靠自觉。** 这个项目做了好几轮**红队回归**（让 AI 扮演攻击者审自己的代码，审完修、修完再审）：审出了一批真问题，后面部署篇细讲。
4. **关键配置要启动时硬校验。** 比如 JWT 密钥（给登录令牌签名的密码）不足 32 位直接拒绝启动——别信"我会记得配"。
5. **动生产数据的脚本必须幂等。** **幂等**就是同一个脚本执行一遍和执行一百遍结果一样：种子脚本重复跑不出错、不重复插入，这是底线。
6. **备份要在第一天建好，不是出事前一天。** 每日备份本地一份、异地一份。
7. **文档是 vibe coding 的上下文资产。** 每次变更同步更新架构文档和 CHANGELOG（变更日志）——三轮对话之后，AI 也不记得你的项目长什么样，文档就是它的记忆。

## 写在最后

系统在生产环境跑了不短的时间，经历过红队回归、服务器迁移、ICP 备案（国内网站上线的法定备案手续）切 TLS（也就是从 http 升级到加密的 https），没出过一次因为"没有 Redis"导致的事故。

但我最想说的不是"AI 真厉害"，而是：**vibe coding 没有消灭架构决策，只是把做决策的方式从"自己想清楚"变成了"把 AI 问清楚"。** 问不清楚的，迟早变成线上事故。
